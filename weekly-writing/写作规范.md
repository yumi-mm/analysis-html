# weekly-writing 写作规范

> 本目录存放**周报相关文本**（版本工作、周会发言、心得体会、领导纪要），与 `analysis/` 目录下的**数据分析、SQL、图表**分离，避免用途混淆。

---

## 一、目录职责对照

| 文件 | 职责 | 受众 | 本质 |
|------|------|------|------|
| `会议记录_测试组版本工作.txt` | 测试组**版本与专项工作台账** | 部门/测试组内部归档 | **事实记录**：做了什么、什么状态 |
| `技术部_领导会议纪要.txt` | 技术部周会**领导发言精炼** | 自己回顾、写心得时对齐方向 | **输入材料**：战略、要求、价值观 |
| `技术部_周会发言.txt` | **本人在技术部周会上的发言稿** | 周会口述 | **对外同步**：进度、风险、亮点数据 |
| `周报_心得体会部分.txt` | 周报中的**心得体会模块** | 周报提交 | **反思总结**：工作 + 体会 + 协作 + 后续 |

### 与 `analysis/` 的区别

| weekly-writing | analysis |
|----------------|----------|
| 版本进度、会议、周报文本 | SQL、分析报告、Excel、图表 HTML |
| 优化**表述与结构** | 查数、作图、口径验证 |
| 参考本目录历史文风 | 参考 `liaoyu-data-analysis` 技能与既有 `.md` |

**向 AI 提需求时请标明类型**，例如：「写版本工作」「写周会发言」「写心得体会」「整理领导纪要」——不要只说「帮我写周报」。

---

## 二、通用格式约定

1. **按日期倒序**：最新内容写在文件**顶部**（领导纪要、版本工作、心得体会、周会发言均如此）。
2. **日期格式**：`07月08日`（月日，不写年份，与历史文件一致）。
3. **编号**：一级用 `1、2、3、`；子项用 `（1）（2）（3）`。
4. **段落缩进**：心得体会段首可用全角空格缩进（与历史一致）。
5. **用语**：`IOS` 保持大写写法（团队习惯，非 Apple 官方 `iOS`）；`达到可发布状态`、`测试验收完成` 等为常用状态表述。

## 三、分文件规范

### 1. 会议记录_测试组版本工作.txt

**职责范围**
- Chamet / WebApp **版本需求**测试与验收状态
- **渠道包**回归（线下包、华为、vivo、oppo、Chaimi 等）
- **专项建设**（Sentry、UI 自动化、埋点自动化等）若属测试组推进，可单列一条
- 不写领导战略、不写个人感想

**结构**
```
版本工作：
07月08日
1、Chamet版本：……
2、WebApp版本：
（1）……
（2）……
3、Chamet各渠道包：……
```

**风格**
- **客观、简短、台账化**
- 每条尽量包含：**事项 + 状态**（已验收 / 可发布 / 已上线 / 待提测）
- 可按产品线分块；WebApp 下多项用（1）（2）

**书写要求（已约定）**
- **尽量少写**「周二提测、周三发布、周四回归」等琐碎排期；优先写**状态结论**
- 确有需要时可保留关键节点（以本人定稿为准）
- 避免空泛，不写「推进中」而无具体事项名

**示例句式**
- `xxx需求已测试验收完成，达到可发布状态。`
- `xxx已完成全量回归测试并发布线上。`
- `Sentry一期配置全部完成，随本版本上线。`

---

### 2. 技术部_领导会议纪要.txt

**职责范围**
- 技术部周会领导发言的**精炼纪要**
- 战略方向、激励政策、排期原则、价值观、协作要求
- **不写**测试组具体版本明细（那是版本工作）

**结构**
```
07月08日
1、主题词：一句话或分号衔接的短说明。
2、……
```

**风格**
- **极精炼**，抓住**一个核心**即可；多数场次 **1～4 条**
- 格式：`主题：说明`，一条一个观点
- 不写测算公式、不写未落地的细节（地点、代表领取等未定事项）
- 不写具体协作纠纷、设计资源争议等操作性内容

**书写要求（已约定）**
- **不要过长**：宁可一条说透，不要六条堆砌
- 参考往期：如 07/02 四条、05/14 两条；07/08 日增7万可**只保留一条**
- 从录音/AI 听记提炼时：**先抓领导最想强调的那一句**

**示例句式**
- `日增7万为关键目标：……各部门在排期和决策时应以此为统一标尺……`
- `拒绝「为了做而做」：不要因为团队空闲就随意启动项目……`

---

### 3. 技术部_周会发言.txt

**职责范围**
- 本人在技术部周会上的**口头同步稿**
- 本周版本进度、渠道包、专项（Sentry）、**有数据支撑的优化效果**
- 可提风险，但比版本工作略口语、更精炼

**结构**
```
会议发言：          ← 文件头（保留历史写法）
07月07日
周会同步：            ← 可选
1、……
2、……
```

**风格**
- **分点列举**，适合**照着念**
- 比版本工作略短；可含**关键数据**（如视频聊占比 9%→11.5%）
- 可写「随本版本上线」「此前在例会上提出」等上下文
- 历史稿中常见相对时间（本周二、明天发布）；新稿可按需简化

**与版本工作的分工**
| 版本工作 | 周会发言 |
|----------|----------|
| 台账，条目更全 | 口述，挑重点 |
| 子项（1）（2）细分 | 常合并为 3～5 条 |
| 归档用 | 当周同步用 |

**注意**：目录中另有 `技术部周会发言.txt`（无下划线），内容与 `_周会发言` 可能重复，**以 `技术部_周会发言.txt` 为准**，避免双份维护。

---

### 4. 周报_心得体会部分.txt

**职责范围**
- 周报里的**「心得体会」**模块（不是工作总结全文）
- 本周重点工作 + **个人角色** + 协作感谢 + **反思/收获** + 后续计划
- 可引用领导纪要方向（如日增7万、数据支撑、抓重点）

**结构**
- 通常 **1～2 段**；多主题可用自然段分开，少用 `1、2、`（与版本工作区分）
- 段首缩进

**风格**
- **第一人称**：`本周我重点推进了`、`我提出的`、`我同步跟踪分析`
- 有**体会**，不只罗列事项（领导 04/22 纪要：心得勿等同于工作总结）
- 适当感谢协作方（贺方姐、志威、湘云等），语气得体
- 有数据分析时写**结论 + 审慎收尾**（如「上线时间较短，还需持续观察」）
- 可结合会议/汇报（丘哥、韬哥、WebApp 例会等）

**书写要求（已约定）**
- 突出**我做的**：推进、验证、跟踪分析、提出优化方向
- 数据结论要写清**业务含义**（如场景占比变化 = 充值回流视频聊）
- 配图时可写「从下图场景结构看」

**示例句式**
- `本周我重点推进了……`
- `此外，我之前提出的两项 WebApp 技术优化也取得了实质进展……`
- `技术改动与业务数据形成了有效印证；但目前上线时间较短，还需要持续观察和验证。`

## 四、四类文档关系（写周报时的顺序建议）

```
领导会议纪要（输入）
       ↓ 对齐方向
版本工作（事实素材） → 周会发言（口述精简版）
       ↓
心得体会（工作 + 反思 + 与领导要求呼应）
```

同一周内容**允许角度不同**，但不要四份完全复制粘贴：
- **版本工作**：最全、最客观
- **周会发言**：精华 + 数据亮点
- **心得体会**：我的贡献 + 体会 + 感谢
- **领导纪要**：只记领导说了什么

## 五、向 AI 发起优化时的推荐话术

| 目标 | 这样说 |
|------|--------|
| 版本工作 | 「按版本工作规范优化，少写周几」 |
| 周会发言 | 「按周会发言风格优化，用于口述」 |
| 心得体会 | 「按心得体会风格，突出我做的」 |
| 领导纪要 | 「按领导纪要风格，只保留一点 / 抓住重点」 |
| SQL / 分析 | 「用 liaoyu 技能写 SQL」→ 产出在 `analysis/`，不写进本目录 |

可提供：**大概要点、录音、AI 听记、是否定稿**，并说明是否**写入对应 txt 顶部**。

---

## 六、常见混淆（避免）

| 错误 | 正确 |
|------|------|
| 把版本进度写进领导纪要 | 领导纪要只写领导观点与要求 |
| 心得体会写成流水账 | 加体会、协作、反思 |
| 周会发言复制整份版本工作 | 精简为 3～5 条口述要点 |
| 在 weekly-writing 里写 SQL | SQL 放 `analysis/` 或对话中输出 |
| 领导纪要写很长带公式 | 一条核心即可 |
| 四份文档混在一个文件 | 严格分文件维护 |
